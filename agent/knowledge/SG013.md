# SG013 — Large-scope DML without LIMIT or batching

A `DELETE`, `UPDATE`, or `INSERT ... SELECT` that operates on a very large
number of rows in a single statement holds locks for the entire duration,
inflates the transaction log, and cannot be safely interrupted once started.

## Why it is dangerous

A single large DML statement is all-or-nothing at commit time, but it is not
all-or-nothing with respect to the side effects that accumulate while it runs:

**Lock contention:** Row-level locks accumulate for every row touched. On a
table with 50 million rows, a `DELETE` without batching holds 50 million row
locks simultaneously. Other transactions that need to write to those rows queue
up behind the lock and timeout. Read queries on engines that take shared locks
(SQL Server, MySQL with certain isolation levels) also queue. The migration
blocks the application for its entire duration.

**Transaction log growth:** Every row deletion or update is written to the
transaction log before the change is visible. A single statement that touches
100 million rows produces a correspondingly large log entry. On instances with
constrained disk, this can exhaust storage and crash the database engine before
the statement completes.

**Cannot be interrupted cleanly:** If the statement is killed mid-execution,
the engine must undo all of the work it has done up to that point — often
taking as long as the forward pass. During the rollback, the locks are still
held. There is no way to "pause and resume" a single DML statement; the only
options are to wait for it to finish or to kill it and wait for the rollback.

**Replication lag:** In replicated setups, the replica must replay the same
large transaction, causing replication lag for the duration. Health checks that
monitor replica lag will alarm.

## The safer pattern

Process large tables in batches with a loop, committing after each batch:

```sql
-- PostgreSQL / MySQL pattern
DO $$
DECLARE
    affected INT := 1;
BEGIN
    WHILE affected > 0 LOOP
        DELETE FROM events
        WHERE id IN (
            SELECT id FROM events
            WHERE processed = TRUE AND created_at < '2023-01-01'
            LIMIT 10000
        );
        GET DIAGNOSTICS affected = ROW_COUNT;
        COMMIT;
    END LOOP;
END $$;
```

For `UPDATE`, the same pattern applies: batch by primary key range or by
`LIMIT`, committing between batches. This keeps locks short, log growth
bounded, and allows the job to be paused or resumed.

A batch size of 1,000–10,000 rows is typical; the right size depends on row
width and index overhead.

## A real incident

A representative failure, of a shape that recurs across published post-mortems:
a migration script runs a single `DELETE` statement to purge several years of
soft-deleted records from a high-traffic table. The table has grown to tens of
millions of rows. The statement acquires row-level locks across the entire
qualifying set and holds them for forty minutes while the engine works through
the deletion. During that window, application writes queue behind the lock and
begin timing out. On replicated setups, the replica must replay the same large
transaction from the binary log; replica lag climbs into the tens of minutes,
causing health checks to alarm and read traffic to be redirected to the primary,
amplifying the load. Even after the primary commit, the replica's catch-up
period extends the disruption. The batch rewrite — deleting in chunks of ten
thousand rows with a commit between each — eliminates all three failure modes:
lock contention stays bounded, log growth is incremental, and the job can be
paused or killed cleanly at any batch boundary.
