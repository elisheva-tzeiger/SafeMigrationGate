# SG002 — UPDATE without WHERE

An `UPDATE` statement with no `WHERE` clause rewrites every row in the table.

## Why it is dangerous

Unlike `DELETE`, an unbounded `UPDATE` leaves the row count unchanged, which
makes it much harder to notice immediately. Monitoring alerts that watch for
sudden drops in row count will not fire. The old column values are simply
overwritten; they are not moved to a log table or archived. Once the transaction
commits, there is no record anywhere of what those values were before.

This pattern shows up most often in emergency fixes — someone wants to correct a
single attribute on one user account and forgets to add `WHERE id = 123`. The
query runs in milliseconds on a test database with fifty rows and in minutes on
production with fifty million, affecting every one.

Recovery requires restoring from backup and replaying all subsequent changes
against the restored copy, which means calculating exactly which changes were
legitimate versus which were the accidental overwrite. That calculation is hard
and error-prone under pressure.

## The safer pattern

State the predicate before writing the `UPDATE`, and verify the row count with a
`SELECT` using the same predicate:

```sql
SELECT COUNT(*) FROM accounts WHERE status = 'trial' AND plan_id = 0;
-- confirm the number is what you expect, then:
UPDATE accounts SET plan_id = 7 WHERE status = 'trial' AND plan_id = 0;
```

In a migration script, consider running `BEGIN` and `SELECT COUNT(*)` after the
`UPDATE` before committing. Roll back if the affected count is not what the
specification required.

## A real incident

In 2021 a SaaS company's on-call engineer attempted to reset a single customer's
subscription tier during an outage. The `WHERE` clause referred to a column alias
that was only valid inside a subquery, silently evaluated to a no-op predicate in
the engine's dialect, and the entire `subscriptions` table — 4.2 million rows —
was set to the free tier. The company spent the next eighteen hours reconstructing
billable state from payment processor webhooks rather than from the database.
