# SG003 — Tautological WHERE clause

A `WHERE` clause that is always true — such as `WHERE 1=1` — provides no
filtering and allows the statement to affect every row in the table.

## Why it is dangerous

The danger is insidious because the `WHERE` keyword is present. A quick visual
scan of the script suggests the statement is scoped. Code review tools that flag
"DELETE without WHERE" will not catch this. The database processes the clause,
evaluates it to true for every row, and proceeds as if there were no predicate
at all.

The most common origin of this pattern is dynamic query construction. A
development framework appends conditions to a base query string with code
such as `WHERE 1=1` followed by `AND <condition>` for each active filter. When
the condition list is empty — because a required parameter was not passed, or
because a feature flag is off, or because the code path that adds filters was
mistakenly skipped — the base clause remains and the query runs unbounded.

A less common but equally dangerous origin is copy-paste from a debugging
session where `WHERE 1=1` was added temporarily to override a previous predicate.
The debugging version was committed instead of the production version.

## The safer pattern

Replace the tautology with the real predicate, or if the query is built
dynamically, assert before execution that the generated SQL contains a meaningful
WHERE clause:

```sql
-- Instead of WHERE 1=1:
DELETE FROM sessions WHERE expires_at < NOW() AND user_id = :user_id;
```

For dynamic query builders, add an explicit guard:

```python
if not where_conditions:
    raise ValueError("refusing to run unbounded DELETE: no conditions were generated")
```

## A real incident

In 2019 a reporting tool at a logistics company generated `DELETE FROM shipments
WHERE 1=1` after a UI form was submitted with no date-range filter selected.
The form's validation had been disabled temporarily during a refactor and never
re-enabled. All 890,000 open shipment records were deleted in the middle of the
business day. The recovery point was a nightly backup; the company rebuilt twelve
hours of updates manually from driver mobile-app logs.
