# SG007 — Column type change

`ALTER TABLE ... ALTER COLUMN ... TYPE` (or the equivalent syntax in each
dialect) changes the data type of an existing column. When the new type is
narrower than the old one, values that do not fit are either silently truncated
or the statement fails partway through.

## Why it is dangerous

A type change is not a metadata-only operation when values must be coerced.
The engine must read every row, cast the stored value to the new type, and
write it back. Two failure modes exist and both are dangerous:

**Silent truncation:** Some engines (notably MySQL in non-strict mode) will
truncate string values that exceed the new length rather than raising an error.
A `VARCHAR(255)` column narrowed to `VARCHAR(50)` silently destroys any stored
value longer than 50 characters. The statement succeeds; no error is reported;
the data is gone.

**Mid-statement failure:** Engines that enforce strict mode or strict typing
(PostgreSQL, SQL Server) will raise an error when a value cannot be cast. If
the statement fails after processing some rows but before completing all of
them, the outcome depends on whether the operation is transactional. On
PostgreSQL the entire `ALTER TABLE` is atomic; on some other engines the table
may be left in a partially-modified state.

Beyond data loss, a type change acquires an `ACCESS EXCLUSIVE` lock (or
equivalent) on the table for its entire duration. On large tables this means
minutes to hours of unavailability. Tooling like `pg_rewrite_table` or online
DDL in MySQL (`ALGORITHM=INPLACE`) can reduce the lock window, but they are
not available in all engines or for all type changes.

The tool cannot compare the existing column type against the new one because
it does not have schema access at analysis time. Any type change therefore
carries risk that cannot be quantified statically.

## The safer pattern

Before issuing the `ALTER TABLE`, verify the existing type and confirm no
stored values will be lost:

```sql
-- Check maximum length of current values before narrowing a string column:
SELECT MAX(LENGTH(email)), COUNT(*) FROM users WHERE LENGTH(email) > 100;

-- If narrowing is safe, consider a zero-downtime approach:
-- 1. Add the new column alongside the old one.
-- 2. Backfill with a batched UPDATE.
-- 3. Switch application code to use the new column.
-- 4. Drop the old column after a validation period.
```

For numeric type changes, cast explicitly and check for out-of-range values
before the migration:

```sql
SELECT COUNT(*) FROM orders WHERE amount > 2147483647; -- INT overflow check
```

## A real incident

MySQL's non-strict mode has produced silent data truncation during migrations.
A representative scenario: a team changes a `TEXT` column to `VARCHAR(500)` to
add an index (MySQL requires a length prefix for `TEXT` indexes). Non-strict
mode silently truncates the 23 rows whose stored values exceed 500 characters.
The migration reports success. The application continues to operate normally.
The truncated data is discovered months later when a customer reports that their
stored address no longer matches their mailing label — well outside the backup
retention window.
