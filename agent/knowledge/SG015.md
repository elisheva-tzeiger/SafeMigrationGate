# SG015 — Privilege change

`GRANT`, `REVOKE`, `CREATE USER`, `ALTER ROLE`, and related privilege
statements change who is permitted to perform which actions on the database.
Unlike data manipulation, privilege changes affect the security boundary of
the entire system.

## Why it is dangerous

A privilege change is not a data operation — it is a security configuration
change. Its effect is immediate and persists indefinitely until explicitly
reversed. Two distinct failure modes exist, both serious:

**Over-granting:** `GRANT ALL PRIVILEGES ON *.* TO app_user` in a migration
script intended to grant read access to a reporting user instead grants
superuser-equivalent access to the application service account. The application
continues to function normally; nothing alerts. The over-grant is discovered
weeks later during a security audit or, worse, after a breach in which the
compromised application account was used to exfiltrate or modify data beyond
what the application should ever have accessed.

**Accidental revocation:** `REVOKE CONNECT ON DATABASE production FROM app_user`
in a script that intended to revoke from a deprecated service account instead
revokes from the live application user. The application loses its database
connection immediately. Depending on connection pooling, the failure may be
silent for minutes before alerts fire.

Neither failure mode is visible to monitoring that watches row counts or query
performance. Privilege changes are logged in the database audit log but not in
application metrics. The impact surface is the entire security model of the
database, not a bounded table or column.

This rule fires as a hard block. There is no automated rewrite that makes a
privilege change safe — the content of the change determines whether it is
correct, and that determination requires human review with knowledge of the
intended security model.

## The safer pattern

There is no safe inline rewrite. Privilege changes must not appear in automated
migration scripts reviewed by this tool.

The required process for any privilege change is:

1. **Author a dedicated change request** — separate from schema or data
   migrations — that describes the current privilege state, the intended new
   state, and the reason for the change.
2. **Review by a security-aware approver** who can assess whether the grant
   or revocation is consistent with the principle of least privilege.
3. **Test in a non-production environment** with the same user/role structure
   as production to confirm the exact effect of each statement.
4. **Execute via a controlled privileged session**, not through the application's
   own service account, with the change logged in the security incident log.
5. **Verify post-execution** that the effective privileges match the intended
   state using `SHOW GRANTS` or the equivalent.

## A real incident

In 2014 Code Spaces, a code hosting service, suffered a permanent shutdown
after an attacker gained access to their AWS control panel and systematically
deleted backups, machine images, and data. While this is a cloud IAM incident
rather than a database privilege incident, the structural lesson is identical:
access control changes are security events, not operational events, and must
be treated with a review process proportional to the damage an incorrect change
can cause. Database `GRANT` statements that reach production through an
unreviewed automated pipeline represent the same risk class.
