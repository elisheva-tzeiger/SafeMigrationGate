# SG009 — Explicit CASCADE

A `CASCADE` option on a `DROP`, `DELETE`, or `TRUNCATE` statement propagates
the operation to dependent objects that are not named anywhere in the script.

## Why it is dangerous

`CASCADE` makes the scope of the operation larger than what is written. A
reader of the script sees one table named; the engine operates on an arbitrary
number of dependent tables, views, indexes, and constraints that are only
visible by inspecting the live schema. The full blast radius of the operation
is invisible at review time.

**DROP TABLE ... CASCADE** removes every view, materialized view, foreign key
constraint, and trigger that depends on the table — recursively. A table that
is referenced by three views, each of which is used by two reporting queries,
drops all five objects silently.

**DELETE ... CASCADE / TRUNCATE ... CASCADE** (PostgreSQL) propagates row
deletions through `ON DELETE CASCADE` foreign key chains. Deleting a single
parent row can remove hundreds of child rows across several tables through
multi-level cascade chains. The child-table deletions do not appear in the
script and are not visible until the schema's constraint graph is followed
manually.

**ALTER TABLE ... DROP COLUMN ... CASCADE** (PostgreSQL) removes all views and
functions that reference the dropped column. This is particularly dangerous
because views are often used by reporting tools that are outside the team's
code repository and therefore outside code search.

The danger is compounded by the fact that `CASCADE` is often added to get past
a constraint error during development and then accidentally committed. "It
worked" is the only signal the developer received; the collateral destruction
happened silently.

## The safer pattern

Remove `CASCADE` and address the dependency directly:

```sql
-- Instead of:
DROP TABLE events CASCADE;

-- Identify and drop dependents explicitly:
DROP VIEW IF EXISTS events_summary;
DROP VIEW IF EXISTS daily_event_counts;
DROP TABLE events;
```

For foreign key chains, make the cascade explicit in the application rather
than in the database constraint. This makes the scope of each operation
visible in the code.

If `CASCADE` is genuinely required (e.g., in a test teardown script), annotate
it clearly:

```sql
-- Intentional cascade: drops events plus these known dependents:
--   views: events_summary, daily_event_counts
--   tables (via FK): event_tags, event_metadata
DROP TABLE events CASCADE;
```

## A real incident

`DROP ... CASCADE` producing unexpected scope is a well-documented class of
production incident. A representative case: a team drops a table they believe
has no dependents, having checked application code for references. The database
schema has a materialized view that was created by a DBA for a reporting
dashboard six months earlier and is not tracked in the application repository.
`CASCADE` silently drops the view. The reporting dashboard begins returning
empty results. Because the dashboard is used by a non-technical team, the
failure is attributed to a data quality issue rather than a schema change for
several days.
