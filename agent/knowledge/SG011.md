# SG011 — Script is not wrapped in a transaction

A migration script that does not open an explicit transaction with `BEGIN` (or
`START TRANSACTION`) has no single rollback point. A failure partway through
leaves the database in a partially-modified state.

## Why it is dangerous

Without a transaction boundary, each statement commits as soon as it succeeds.
If the script contains five statements and the fourth fails, the first three are
permanently committed and the fifth has not run. The database is now in a state
that was never intended and that the script cannot reach from its starting
position because statements 1–3 cannot be re-executed (they may violate unique
constraints, or they may have modified data that subsequent logic depends on).

Recovery from partial application is manual and time-consuming: the operator
must identify which statements succeeded, determine the resulting intermediate
state, and write compensating statements to move the database forward or
backward. Under production pressure, this is error-prone.

The risk is highest for scripts that combine a `DELETE` or `UPDATE` with a
preceding `ALTER TABLE`. If the `ALTER` succeeds and the `DELETE` fails, the
schema change is permanent. Application code may be deployed expecting both
changes to be in effect.

Many engines auto-commit DDL statements regardless of any surrounding
transaction (see SG012), but for DML-only scripts a transaction provides a
reliable safety net.

## The safer pattern

Wrap every migration script in an explicit transaction with a guard:

```sql
BEGIN;

-- All migration statements go here
UPDATE accounts SET plan_id = 7 WHERE status = 'trial' AND plan_id = 0;
INSERT INTO migration_log (name, applied_at) VALUES ('backfill_plan_id', NOW());

-- Verify the expected row count before committing:
DO $$
BEGIN
    IF (SELECT COUNT(*) FROM accounts WHERE plan_id = 0 AND status = 'trial') > 0 THEN
        RAISE EXCEPTION 'backfill did not complete cleanly, rolling back';
    END IF;
END $$;

COMMIT;
```

For engines that auto-commit DDL, separate DDL migrations from DML migrations
into different scripts, each with their own transaction where possible.

## A real incident

A representative pattern from on-call post-mortems: a ten-statement DML
migration runs without a transaction. Statement seven fails because a unique
index was not yet created on the target column. Statements one through six have
already committed. The migration tooling marks the migration as "failed" and
the on-call engineer re-runs it. Because statement two was an `INSERT` without
`IF NOT EXISTS`, it now raises a duplicate-key violation. The team must write
a manual compensation script to undo statement six before the migration can be
re-run safely, and must do so under the pressure of a deployment that is
blocked waiting for the database to be consistent.
