# SG012 — DDL and DML mixed in one script

A script that contains both DDL statements (such as `ALTER TABLE`, `DROP TABLE`,
`CREATE TABLE`, or `TRUNCATE`) and DML statements (such as `DELETE`, `UPDATE`,
or `INSERT`) cannot be fully rolled back as a unit on many database engines,
because DDL triggers an implicit commit.

## Why it is dangerous

On MySQL, Oracle, and several other engines, DDL statements perform an implicit
`COMMIT` of any open transaction immediately before executing. This means that
DML statements that appeared earlier in the script — and that the operator
intended to be part of the same atomic unit — are committed permanently before
the DDL executes. If the DDL then fails, the earlier DML cannot be rolled back.

```sql
-- On MySQL, this is NOT atomic:
BEGIN;
UPDATE accounts SET status = 'migrated' WHERE legacy = TRUE;  -- commits here (implicit)
ALTER TABLE accounts ADD COLUMN migrated_at TIMESTAMP;        -- DDL triggers implicit commit
COMMIT;
-- If ALTER TABLE fails, the UPDATE is already committed.
```

On PostgreSQL, most DDL is transactional (it can be rolled back), but
`CREATE DATABASE`, `DROP DATABASE`, `VACUUM`, `REINDEX CONCURRENTLY`, and a
few others are not. A script mixing these with DML has the same exposure.

Even on engines where DDL is transactional, mixing DDL and DML in one migration
script creates a coupling that makes the migration harder to reason about,
harder to re-run, and harder to apply with online DDL tools (which often require
the DDL to be isolated).

## The safer pattern

Separate DDL migrations from DML migrations into distinct scripts with distinct
transaction boundaries:

**Migration 001 (DDL only):**
```sql
BEGIN;
ALTER TABLE accounts ADD COLUMN migrated_at TIMESTAMP;
COMMIT;
```

**Migration 002 (DML only, runs after 001):**
```sql
BEGIN;
UPDATE accounts SET migrated_at = NOW() WHERE legacy = TRUE;
COMMIT;
```

This approach is compatible with standard migration frameworks (Flyway, Liquibase,
Alembic) which run each numbered migration in isolation.

## A real incident

MySQL's implicit-commit behaviour has produced partial-migration states in
production deployments. A representative scenario: a team runs a migration that
first updates a column to mark rows as processed, then drops a legacy column.
The `ALTER TABLE ... DROP COLUMN` issues an implicit commit of the `UPDATE`
before executing. The `ALTER TABLE` then fails because the column has a
dependent index that was not accounted for. The team rolls back — but the
`UPDATE` has already committed. The migration state is now half-applied:
processed rows are marked as processed, but the legacy column still exists.
Re-running the migration produces duplicate processing for those rows.
