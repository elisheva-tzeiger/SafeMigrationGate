# SG014 — DROP DATABASE / DROP SCHEMA

`DROP DATABASE` or `DROP SCHEMA` removes an entire namespace — every table,
view, index, stored procedure, sequence, and the data in all of them — in a
single statement.

## Why it is dangerous

There is no operation in routine database management that is more
unrecoverable. A `DROP DATABASE` destroys:

- Every table and every row those tables contain.
- Every view, materialized view, and stored procedure defined in the schema.
- Every index, trigger, and sequence.
- All permissions and grants defined within the namespace.

The statement completes in seconds regardless of how much data it destroys,
because the engine deallocates storage blocks rather than removing rows one
by one. There is no log of what was lost that can be used for recovery.
Recovery requires restoring from the most recent backup — every change made
to the database after that backup is permanently lost.

Unlike `DROP TABLE`, which affects a bounded, nameable object, `DROP DATABASE`
affects everything. On engines where a schema namespace is shared across
multiple application teams (a common pattern in Oracle and SQL Server
deployments), a `DROP SCHEMA` can destroy another team's data alongside the
intended target.

This rule fires as a hard block. There is no safe rewrite of `DROP DATABASE`
or `DROP SCHEMA` that preserves the intent while reducing risk. The only
appropriate path is a deliberate, reviewed, out-of-band operation.

## The safer pattern

There is no safe inline rewrite. `DROP DATABASE` and `DROP SCHEMA` must not
appear in automated migration scripts reviewed by this tool.

If decommissioning a database or schema is genuinely the goal, the required
process is:

1. **Obtain explicit written approval** from the database owner and an
   independent technical reviewer who has confirmed the list of objects that
   will be destroyed.
2. **Take a verified backup immediately before execution** and confirm the
   backup is restorable on a test instance.
3. **Rename rather than drop** to preserve data during an observation period:
   `ALTER SCHEMA production_events RENAME TO production_events_deprecated_20240901;`
4. **Execute in a controlled maintenance window** with the on-call engineer
   present and the backup confirmed, not through an automated CI pipeline.
5. **Drop only after the observation period has passed** and all dependent
   systems have been confirmed to be free of references.

## A real incident

A representative failure, of a shape that recurs across published post-mortems:
an on-call engineer is working through a routine decommissioning task late in a
maintenance window. The target environment is a staging namespace. A missing
qualifier in the connection string means the session is pointed at production.
The engineer runs `DROP DATABASE` and confirms the prompt. The database engine
completes the operation in under three seconds, removing every table, every row,
every view, and every stored procedure. The monitoring system raises a cascade of
alerts as dependent services begin to fail. Recovery requires restoring from the
previous night's backup; all writes made in the intervening hours are gone
permanently. The scope of a `DROP DATABASE` — the entire namespace — is what
makes a single moment of inattention unrecoverable in a way that no other
routine SQL statement is.
