# SG005 — TRUNCATE

`TRUNCATE` removes all rows from a table faster than `DELETE` by deallocating
data pages rather than logging each row removal individually.

## Why it is dangerous

The speed advantage comes from a deliberate trade-off: because individual row
deletions are not written to the transaction log, there is no row-level undo
available. A `DELETE FROM t` inside a transaction can be rolled back by
replaying the log. A `TRUNCATE` in the same transaction cannot be replayed
at row granularity — recovery requires restoring from a backup.

The behaviour is engine-dependent in a way that surprises operators:

- **PostgreSQL** treats `TRUNCATE` as a transactional DDL statement, so it
  can be rolled back inside an explicit transaction — but it acquires an
  `ACCESS EXCLUSIVE` lock that blocks all other readers and writers for the
  duration.
- **MySQL and Oracle** treat `TRUNCATE` as DDL and issue an *implicit commit*
  before executing it. Any DML in the same session that has not yet been
  committed is committed automatically before the truncation begins. There is
  no way to roll back either that DML or the truncation.
- **SQL Server** allows `TRUNCATE` to be rolled back inside an explicit
  transaction, but the minimal logging means the log file does not grow,
  which can mislead operators who use log growth as a proxy for "this is
  still running".

The implicit-commit behaviour on MySQL and Oracle is the sharpest edge: a
script that mixes `UPDATE` statements with a `TRUNCATE` may commit the
updates permanently before the operator intended.

## The safer pattern

If the goal is to empty a table during a migration, use a bounded `DELETE`
with a `LIMIT` clause and loop until no rows remain. This is slower but
produces a log that can be replayed:

```sql
-- PostgreSQL / SQL Server
DELETE FROM staging_events WHERE processed_at < '2024-01-01' LIMIT 10000;
-- repeat until 0 rows affected

-- or, if you need to empty the table in one statement and can accept the
-- lock, wrap it in an explicit transaction and verify the row count first:
BEGIN;
SELECT COUNT(*) FROM staging_events; -- verify intent
TRUNCATE staging_events;
ROLLBACK; -- review, then COMMIT if correct
```

On MySQL or Oracle, never place `TRUNCATE` in a script alongside uncommitted
DML you expect to be able to roll back together.

## A real incident

MySQL's implicit-commit behaviour has caught teams during routine data-cleanup
migrations. A representative pattern: a script begins with several `UPDATE`
statements intended to backfill a new column, then calls `TRUNCATE` on a
staging table to reset it. On MySQL the `TRUNCATE` silently commits the
`UPDATE`s that preceded it, so a subsequent error that causes the operator
to roll back the "transaction" finds there is nothing left to roll back — the
backfill is already permanent. The staging table is also empty, making it
impossible to re-run the migration idempotently without restoring it first.
