# SG006 — ALTER TABLE ... DROP COLUMN

`ALTER TABLE ... DROP COLUMN` removes a column and all of the data it contains
from the table permanently.

## Why it is dangerous

The column's data is gone the moment the statement commits. Unlike dropping a
row, there is no row-granularity undo available: the values that were stored in
that column do not appear in the transaction log in a recoverable form on most
engines. Recovery requires a full table restore from backup.

More insidiously, the breakage does not always surface immediately. Application
code that constructs `SELECT *` queries will stop receiving the column in the
result set without raising an error. Code that names the column explicitly —
`SELECT user_id, deprecated_field FROM accounts` — will fail with an
"unknown column" error the first time it executes after the migration. If that
code path is hit infrequently (a monthly report, a background job) the failure
may not be discovered until long after the backup retention window has closed.

Indexes defined on the dropped column are removed silently. Foreign keys that
reference the column will prevent the drop on engines that enforce them
(PostgreSQL, SQL Server), but on MySQL with `SET FOREIGN_KEY_CHECKS=0` they
will be silently left as dangling references. Triggers that reference the
column by name will fail at execution time rather than at definition time.

## The safer pattern

Use the expand-contract pattern across two separate deployment cycles:

**Cycle 1 — contract the application:**
Stop writing to and reading from the column in application code. Deploy and
verify. Mark the column nullable with a comment: `ALTER TABLE t MODIFY COLUMN
deprecated_field VARCHAR(255) COMMENT 'UNUSED — pending removal 2024-Q3';`

**Cycle 2 — remove the column:**
After at least one full release cycle with monitoring confirming the column
receives no reads or writes, issue the `DROP COLUMN`. By this point any
application code that still depends on it will have surfaced in staging.

```sql
-- Only in Cycle 2, after validation:
ALTER TABLE accounts DROP COLUMN deprecated_field;
```

## A real incident

A representative pattern: a team removes a column that their code search
confirmed is unused in the main application. A third-party analytics connector
configured in the data warehouse team's tools queries the table with a
hardcoded column list. The connector breaks silently — it logs an error but
does not alert — and the data warehouse stops receiving that column's history.
The gap is discovered three weeks later when a quarterly report shows
anomalous nulls. By then the backup retention policy (14 days) has expired and
the historical values cannot be recovered.
