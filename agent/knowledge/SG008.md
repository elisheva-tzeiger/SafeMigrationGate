# SG008 — UPDATE on a key column

An `UPDATE` that modifies a primary key, surrogate key, or foreign key column
breaks referential integrity for every other table and external system that
holds the old value.

## Why it is dangerous

A key column is an identity: other rows, other tables, external caches, message
queues, URLs, and third-party integrations all refer to a row by its key value.
Changing that value in the database does not automatically propagate the change
anywhere else.

**Orphaned foreign keys:** Tables with a foreign key pointing to the old value
will either raise a constraint violation (on engines that check at update time)
or silently hold a value that no longer matches any parent row (on engines with
deferred constraint checking or with foreign keys disabled). Either outcome
corrupts the join results that application code relies on.

**Stale external references:** APIs that return a resource at `/users/42` will
continue to serve requests for `/users/42` using the application's cache or
the external client's bookmark. After the key is updated to `43`, those requests
resolve to a different row — or return 404 — while the client believes it is
still working with the same entity.

**Event log corruption:** Event-driven architectures emit events keyed by the
entity's id. An `order_id` that appears in a Kafka topic, an S3 path, or an
audit log cannot be retroactively updated. After the key change the event
history refers to a key that no longer exists.

The rule fires on column names that match common key patterns (`id`, `uuid`,
`guid`, `pk`, `*_id`) at analysis time, without schema access. A column named
`device_id` that is the primary key and a column also named `device_id` that
is a plain attribute are indistinguishable statically; the rule fires on both
and accepts false positives as the safer trade-off.

## The safer pattern

Rather than updating a key column, treat the key as immutable and model the
change through the application:

1. Insert the new row with the new key.
2. Copy or re-associate all dependent rows to the new key.
3. Delete the old row after all references have been migrated.

If the goal is to correct a key that was generated incorrectly (e.g. a UUID
that was populated with the wrong algorithm), do so within a transaction and
update all foreign-key references in the same transaction:

```sql
BEGIN;
INSERT INTO users (id, name, email) SELECT 'new-uuid', name, email FROM users WHERE id = 'old-uuid';
UPDATE orders SET user_id = 'new-uuid' WHERE user_id = 'old-uuid';
DELETE FROM users WHERE id = 'old-uuid';
COMMIT;
```

## A real incident

A representative scenario: a team discovers that a subset of user records was
assigned sequential integer ids instead of the intended UUIDs due to a bug in
a data import script. A bulk `UPDATE users SET id = gen_random_uuid() WHERE id
< 1000` is issued. The `sessions` table holds `user_id` as a foreign key with
`ON UPDATE NO ACTION`; the update raises a constraint violation. To work around
it, foreign key checks are disabled for the session. The update succeeds. The
`sessions` rows now reference user ids that do not exist, and every session for
those users is invalidated, logging out approximately 900 active users
mid-session without warning.
