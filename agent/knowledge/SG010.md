# SG010 — WHERE depends on an unbounded subquery

A `DELETE` or `UPDATE` whose `WHERE` clause contains a subquery with no
`LIMIT` affects every row that the subquery returns at execution time —
a set that may be much larger than what was tested or intended.

## Why it is dangerous

A subquery-driven `WHERE` clause looks scoped, but the scope is determined by
what the subquery returns at the moment the statement runs in production,
not by what it returned when the developer tested it.

```sql
DELETE FROM events WHERE user_id IN (
    SELECT id FROM users WHERE status = 'deleted'
);
```

At test time, five users had `status = 'deleted'`. At 2 AM on the day the
migration runs in production, 85,000 users have that status because a background
job processed a batch earlier in the evening. The `DELETE` removes 85,000 users'
events rather than five test users' events.

The problem is structural: the subquery's result set is determined by live data,
not by the script. A reviewer cannot know from reading the script how many rows
will be affected. The operator cannot know unless they run the subquery against
production immediately before the migration and compare the count.

A second failure mode is plan instability: on large tables the query planner may
choose different join strategies between test and production, producing a
different result set if the subquery is not referentially transparent (e.g., it
calls a function with side effects, reads from a table that changes between
query planning and execution in a read-committed isolation level).

## The safer pattern

Materialize the subquery into a temporary table first, inspect its contents,
and drive the DML from the temporary table:

```sql
-- Step 1: capture the set
CREATE TEMP TABLE users_to_delete AS
    SELECT id FROM users WHERE status = 'deleted';

-- Step 2: verify the count before deleting
SELECT COUNT(*) FROM users_to_delete;
-- ^^ review this number before continuing

-- Step 3: execute bounded DML
DELETE FROM events WHERE user_id IN (SELECT id FROM users_to_delete);
DROP TABLE users_to_delete;
```

Alternatively, add an explicit `LIMIT` to the subquery to enforce an upper
bound:

```sql
DELETE FROM events WHERE user_id IN (
    SELECT id FROM users WHERE status = 'deleted' LIMIT 100
);
```

## A real incident

A representative scenario: a cleanup job deletes audit records for users whose
accounts were closed more than two years ago. The subquery selects from the
`accounts` table. A separate, unrelated migration that ran earlier in the same
release changes the `closed_at` column's default value, causing a large
historical cohort of accounts to match the `closed_at < NOW() - INTERVAL 2 YEAR`
predicate unexpectedly. The cleanup job deletes three years of audit records
rather than two years. The compliance team's quarterly audit report for the
previous period can no longer be reproduced from the database.
